# OpenSandbox on Amazon EKS, part 6: the stress test

Companion code for part 6 of the my2cents.ai series "OpenSandbox on Amazon EKS". It pushes the cluster from part 2 until something gives, and measures what gives first:

- **density**: how many idle sandboxes two nodes take, without and with the egress sidecar, and under Kata, and which resource runs out;
- **create latency** under concurrency, cold and from a Pool, and how fast a Pool hands out sandboxes;
- **a pause storm**: 20 sandboxes with 100 MiB each pause to ECR at once, then resume;
- **the egress overhead ladder**: the same requests through each layer of egress control, from no policy to the SigV4 addon of part 5, and what each sidecar holds in memory;
- **the control plane**: what the lifecycle server and the controller use as API calls and create waves ramp up;
- **noisy neighbors**: what CPU and disk hogs do to the sandboxes next to them, under runc and Kata.

Video walkthrough: https://youtu.be/sPxoLhn7xBY

## What you need first

Every script here builds on the earlier parts' directories, which must sit next to this one:

- [`../opensandbox-eks`](../opensandbox-eks) (part 2): `01_cluster.sh` to `05_gateway.sh`. Its `env.sh`, its `.env` (the API key) and its `common.py` are used from here, and `01_metrics.sh` plans its Terraform.
- [`../opensandbox-lifecycle`](../opensandbox-lifecycle) (part 3): `server_config.py`, through which every server change here goes; its `common.py` (the port-forward keeper); and `00_snapshot_config.sh`, which `04_pause_storm.py` needs run within the hour before. That script upgrades the controller release with the snapshot settings and writes a fresh 12-hour ECR token; it is not only a token refresh.
- [`../opensandbox-aws-credentials`](../opensandbox-aws-credentials) (part 5), for the ladder's SigV4 rung only: `01_iam.sh`, `00_image.sh` (the `aws-tools:1` image) and `02_broker.sh` (the broker), and its `build_egress.sh`, which this directory runs to switch the server to the `egress-sigv4` image. That script needs Docker with buildx and uv even when it does not rebuild. `05_egress_ladder.py --rungs none,dns,dns+nft,mitm,vault` leaves the rung out.

The echo server the ladder calls is this directory's own (`manifests/echo-stress.yaml`: part 4's echo program in 3 replicas, sized for load). `05_egress_ladder.py` creates it and deletes it, so part 4's echo server need not be running.

Tools: [`uv`](https://docs.astral.sh/uv/), Python 3.11 or later, `kubectl`, Helm 3, Terraform 1.9 or later, the AWS CLI v2, `jq`; Docker with buildx for the ladder's SigV4 rung (`05_egress_ladder.py` checks for it and for uv before it measures). Run `uv sync` once here. `pyproject.toml` pins `opensandbox==1.2.0` and adds matplotlib for the charts.

The server port-forward on `127.0.0.1:18080` is started for you and restarted whenever a server change replaces the pod. Don't run a port-forward of your own on 18080 during part 6: when it points at a replaced server pod, the scripts cannot take the port over and stop after 45 seconds. No script prints the API key, an account ID, an ARN, the EKS endpoint, a load balancer name, an IP address or a home directory path.

Container Insights is on during every measurement (its agent DaemonSet runs on both nodes and reads the kubelet too). It is part of the setup the numbers come from, and `99_cleanup.py` turns it off.

## The same two nodes

Every number here comes from the same cluster: two `m7i.2xlarge` nodes (8 vCPU, 32 GiB each, nested virtualization for Kata), with no autoscaler. Some ceilings are those of this node type, not of OpenSandbox. A node takes 58 pods, the VPC CNI's limit for `m7i.2xlarge` without prefix delegation, and the system pods already use about 27 of the 116. The scripts report which limit they hit, so a reader with other nodes can tell which numbers move.

## How the measurements are made

- **RUNS.** Every measurement runs `RUNS` times (default 3; `RUNS=1 uv run python ...` for a quick pass), and the results give the median and the spread (max - min) of the repeats next to the pooled percentiles.
- **A quiet cluster first.** Before measuring, each script checks that the server lists no sandboxes (this directory's, or any other part's), that no Pool and no stray BatchSandbox exists, that none of this directory's own objects are left (the echo server, a VM sampler, the API load Job, the latency client), that the server runs runc with the base egress image in `dns+nft` mode with the gateway (`server_config.py --show --json`) on a Helm release whose latest revision is the deployed one, and that both nodes are Ready. It refuses to start otherwise. Other pods in the sandbox namespace (part 4's echo server, say) are named, not refused.
- **Failures are never samples.** A failed create, request, resume or claim is counted, written to the results and printed; it never enters a latency list. A run with any failure is marked and left out of the medians (or, when every run had one, the median is flagged). A density run that stopped on an error is not a ceiling.
- **Labels.** Every sandbox made here carries the metadata `example=opensandbox-stress`, and the clean-ups delete that label only.
- **The server always comes back.** A script that changes the server (Kata, the egress mode, the SigV4 image) does it through `server_config.py` and, in a `finally`, always runs `server_config.py --baseline` once any change was attempted (a failed Helm upgrade leaves its objects live while `--show` still reports the previous revision, so `--show` alone is not trusted), waits for a pending Helm operation first, and reads the result back both ways: `--show --json` and Helm's history. `server_config.py` and part 5's `build_egress.sh` run in their own session, so Ctrl-C reaches only the script, which waits for the change to finish before it stops; SIGTERM ends a script like an exception, so its `finally` blocks run. So does SIGHUP (a closed terminal): the script first points its output at `logs/hangup.log`, because the terminal is gone and a print to it would fail, then deletes what it made and puts the server back; read that file to see how the clean-up went. A Ctrl-C or a signal during a delete stops the script there (after its `finally` blocks), it does not measure on.
- **`--dry-run`.** Every script prints its plan with `--dry-run`: the checks, the steps with an estimate, what it changes on the server and what it puts back. A dry run calls no `kubectl`, `helm`, `terraform` or `aws` (the tests check this).
- **The sampler.** While a script runs, the kubelet's `stats/summary` of both nodes is read every 2 or 5 seconds into `results/<name>.csv` with the columns `t,node,pod,cpu_m,mem_mib`: seconds since the start, the node (`node-a`, `node-b`), the pod (`_node` for the node's total), millicores, and the working set in MiB. `02`, `05` and `06` also write `results/<name>-containers.csv`, one row per container with its RSS, which is where the egress sidecar's memory comes from.

### 02: density

The sandboxes are idle and small (`--cpu 100m --memory 128Mi`, requests = limits), so what limits them is the platform's own cost per sandbox, not a workload. With the sidecar, each sandbox also gets the egress container with its DNS proxy, nftables and the transparent proxy (`credentialProxy` on, as parts 4 and 5 run it). The server sets no `[egress]` requests, so the sidecar asks the scheduler for nothing: the count the scheduler allows does not change, the memory the nodes really use does. Two numbers give that cost. `egress_memory_ratio` compares the pods' working sets. `egress_node_cost_mib` is the node working-set growth per sandbox with the sidecar minus without it, which is what the nodes pay. Under Kata the RuntimeClass adds 250m CPU and 160Mi to every pod's request. On this cluster's Kubernetes 1.37, the scheduler counts a bound pod's RuntimeClass overhead twice (kubernetes/kubernetes#143257; fix PR #143263 unmerged as of November 7, 2026). So each running Kata sandbox costs it about 600m instead of 350m, and the nodes refuse at 12 sandboxes each with CPU to spare (`probes/kata_ceiling.py`, `probes/kata_plain.py`). `--modes runc-policy` adds a run with a policy but no transparent proxy.

The Kata nodes run with `sandbox_cgroup_only = false` (in `configuration-qemu.toml`), so part of what a VM's processes (QEMU, virtiofsd, the Kata shim) use may be accounted outside the pod's cgroup. Rather than rely on how Kata splits it, the script measures what the kubelet's pod number (and with it `kubectl top` and memory evictions) leaves out. For the Kata runs the script puts a sampler pod on each node (`manifests/vmm-sampler.yaml`: busybox, privileged, sharing the node's process table, reading `/proc` and nothing else, deleted afterwards). It records every VM's resident memory, finds the pod each VM belongs to from the sandbox's OCI bundle under `/run/containerd`, and the results set it beside the kubelet's number for the same pod, with where that number came from (`mem_source`: the pod cgroup, or the containers' sum): `node_side` in `results/density.json` and every sample in `results/density-vmm.csv` (`t,node,pod,kind,rss_mib`). Summing RSS overstates what a VM costs. A page that several processes map counts once in each, and QEMU and virtiofsd both map the guest's RAM, so the sum, and its gap to the kubelet's number, is an upper bound. What one more sandbox really costs is how much the nodes' working set grows per sandbox added: `node_growth_mib`, measured from the first batch to the last one before a create failed. `node_growth_span` says how many sandboxes that covers: under Kata the cluster refuses the third batch, so the growth rests on one 10-sandbox step. The chart sets four numbers side by side: the kubelet's, that growth, the RSS sum, and the scheduler's reservation (the request plus the RuntimeClass's 160Mi). The sampler's logs are read every 20 s while it runs, and its pods are deleted first at the end, whatever happens to the last log read; its image is pinned by digest.

`uv run python 02_density.py --resummarize` recomputes these summaries from the runs stored in `results/density.json`, with no cluster calls. With `--dry-run` it prints them and writes nothing.

When a create fails, the server has already deleted the sandbox whose create timed out, so the script keeps every pod it saw the scheduler fail to place and reads the reason from it (`Too many pods`, `Insufficient cpu`, ...), or from the FailedScheduling event.

### 03: create latency and Pools

A create is timed from the SDK call until the sandbox answers its health check, as a user waits for it, at 250m / 512Mi so that 40 at once fit. The timing runs inside the cluster: a client pod in `opensandbox-system` (`manifests/latency-client.yaml`, `loadgen/create_latency.py`) calls the server's Service. It installs the SDK from `loadgen/client-requirements.txt`: `opensandbox==1.2.0` and every dependency at the versions of this directory's `uv.lock`, each with its hashes, wheels only, because the pod holds the API key; a failed install stops the script at once with the end of the pod's log. The client also reports its own CPU per round, and a round where it used 800m or more (it is one Python process) is flagged client-bound. The laptop drives it one round at a time with `kubectl exec`. From the laptop, the port-forward would carry every create and every health-check poll of 40 creates at once and be part of what is measured. One cold/warm pair at one create at a time also runs from the laptop through the port-forward, labelled "via port-forward" everywhere, so the numbers can be set beside part 3's; the two paths are never mixed. `results/latency.json` records the client of every number (`client`).

Small levels run more rounds, so every level has at least 30 samples; one discarded create warms each path first. p50 and p95 are reported: below 100 samples the nearest-rank p99 is the maximum. The warm creates take a pod from the Pool `osb-stress-pool` (`manifests/pool.yaml`; part 3's is `osb-pool`), which may not grow past its 40 pods: rounds keep their sandboxes while the Pool has enough left, then all are deleted and the Pool is waited back to full, so no replacement pod starts during a measured round. The controller's single claims are held the same way.

The controller-path claims apply a BatchSandbox with `poolRef` straight to the Kubernetes API (through `kubectl proxy`, timed with a watch), so they leave out the lifecycle server, the SDK and the health check. The laptop's round trip to the API server is recorded next to them. A claim that is not ready within 180 s is counted as timed out, not timed.

Two published reference points are printed next to our numbers, not reproduced:

- the release's operator docs (`docs/architecture/control-plane/operator.md`): "measured delivery of 100 sandboxes" with pooling, 0.92 s for a BatchSandbox. No hardware or setup is given, so read it as an illustration.
- an [AWS China blog post](https://aws.amazon.com/cn/blogs/china/amazon-eks-build-security-ai-agent/) (2026-07-15): about 230 ms to claim a sandbox from a warm Pool and about 3.1 s cold, with the controller only (no lifecycle server, egress sidecar or ingress), Kata with Cloud Hypervisor, on `c5.metal`.

100 pods do not fit on these two nodes next to the system pods (see "The same two nodes"). The delivery test works out how many do when it runs, and prints the reason with the number, in the recorded run "58 pod slots per node x 2 nodes = 116, minus 28 pods already placed (system pods), minus 4 headroom = 84: 84 instead of 100".

### 04: the pause storm

The data is random so that the compressed snapshot layer is as big as the data. "Durable" is the moment a sandbox's SandboxSnapshot reaches `Succeed` (its commit Job pushed the image). Pushes to ECR go through the NAT gateway, as `08_cloudwatch.py` shows; the resumes moved next to nothing through it, so either their pulls came through the VPC's S3 gateway endpoint or the node still had the image, and the run doesn't say which. CloudWatch gives the NAT gateway's bytes as one-minute points, and the storms run about a minute apart. So 08 pads each pause window by one point on each side, merges windows that overlap, and counts each point once. A storm gets its own figure only when every storm in the group has its own busy minute, and those minutes hold at least 98% of the group's bytes (the rest is `unattributed_bytes`). A storm's bytes show up in the minute after the one its pause falls in. That is the NAT gateway's own timing (the laptop's and the nodes' clocks agree to a few seconds), and it's why the windows are padded. Expect about the fresh data (`--size` x `--mb` MiB) plus a few percent. ECR's image sizes are larger, because they also count each image's base layers, which the registry already holds and a push skips. `08_cloudwatch.py --resummarize` recomputes these figures from the saved series, with no AWS calls (with `--dry-run`, it writes nothing). `--egress` gives each sandbox the sidecar, which makes two snapshot images per sandbox. The images stay in ECR until `99_cleanup.py`.

### 05: the egress ladder

Rungs 1 to 5 call `echo-stress.opensandbox.svc.cluster.local` over plain HTTP on port 80, with a new connection per request (a lookup, a connect, a GET, a close), from a fresh sandbox per run: 500 requests one at a time, then 16 clients for 30 s. The transparent proxy rung therefore pays the proxy's own cost and no TLS handshake. The echo server (`manifests/echo-stress.yaml`) is part 4's echo program and image in 3 replicas of 500m (limit 1 CPU each); the script applies it before the first rung and deletes it after the last, also on failure. Each replica is one Python process, which runs Python on one core at a time, and every request is a new connection, so the Service spreads the load over the three. The sampler reads every replica: a rung where any of them reached 800m (80% of its core) is flagged, because that rung's requests per second are then the echo server's ceiling, not the path's. Each replica's numbers are in `results/ladder.json`. The load phase runs in 4 processes, and a run where the load generator's own CPU reached 1600m (80% of its 2 CPUs) is flagged "client-bound". Both flags use the CPU averaged over the load phase from the kubelet's cumulative counters: the readings are chosen by the kubelet's own timestamps inside the load phase as the load generator timed it, and they must be at least 10 s apart (the kubelet refreshes them about every 10 s, hence the 30-second load phase). Without such readings the CPU is "unknown": printed and counted as such, never taken as "not the cap". A run with a failed request is marked and left out of the medians. If `build_egress.sh` had to rebuild the SigV4 image, the script says so and records it (`sigv4_rebuilt`).

In `dns+nft` mode the lookup through the sidecar takes about 60 ms, against 0.3 ms in `dns` mode. Each request makes a new connection and so a new lookup, which means the lookup dominates every rung that runs in `dns+nft` mode (`dns+nft`, the proxy, the vault). Each run's lookups are timed on their own (`lookup` in `results/ladder.json`). `uv run python 05_egress_ladder.py --resolve-once` is a variant that takes the lookup out. Each run looks the echo host up once, records that time (about 60 ms in `dns+nft` mode), and then opens every connection to the cached address: a connect, the GET and the close. The `Host` header still names the service, which is what the vault binding matches. The variant runs `none`, `dns+nft`, `mitm` and `vault`, RUNS times each with the same phases and checks, and labels them `<rung>/cached`. It writes `results/ladder-resolve-once.json`, `.csv` and `-containers.csv` and leaves `results/ladder.json` alone. Its summary sets each rung's one-at-a-time mean beside the main ladder's connect + GET + close mean (the request's mean minus the lookup's). If a cached rung reaches the echo server's ceiling (target-bound), its ratio against `dns+nft` is only a bound, so the variant runs that pair once more with 8 clients (`@8`). If nftables lets an allowed address expire, requests to the cached address start failing partway through a run. Those failures are the result: they are counted by kind, with the seconds since the lookup, and never timed. A run is called `expired` when no request succeeded after the first failure (nothing renews the address without a new lookup), and `isolated` when requests went on succeeding. Requests in the variant time out after 4 s; the main ladder used `http_load.py`'s default of 10 s. That only decides which slow connections count as failures, and 4 s still lets a connection through after two SYN retransmits (1 s and 3 s). A one-at-a-time phase ends after 20 failures in a row, so a dead address can't stall a run. About 13 min, plus about 4 min if a cached rung is target-bound.

The SigV4 rung calls AWS STS for real, because the addon kills any host that is not AWS: part 5's broker makes the sandbox and writes short-lived credentials into its vault, the sandbox holds placeholders only. Its time includes AWS's own latency; the "aws-floor" row is the same call unsigned from a sandbox with no sidecar (AWS answers 403 at once). The script runs `build_egress.sh`, which does not rebuild an image already in ECR, and reads the image the server then runs from `server_config.py --show --json`.

The published reference is the egress component's benchmark (`components/egress/docs/benchmark.md` in the 1.2.0 release, "illustrative only"): with the transparent proxy, about -48% requests per second, +92% mean latency, +595% p99 and about 5x the sidecar's RSS, for short HTTPS requests to public sites. Ours is HTTP inside the cluster, so the two are printed side by side.

### 06: the control plane

The API ramp runs in a Job next to the server (`manifests/api-load.yaml`, `loadgen/api_load.py`): from the laptop, the `kubectl port-forward` would be the bottleneck being measured. The Job reads the API key from the server's own Secret. The server has one replica with a 1-CPU limit and SQLite on an EBS volume, so its requests per second level off where that CPU runs out. Each level runs 30 s, and the server's and the controller's CPU per level is averaged from their cumulative counters over the level as the Job timed it (readings at least 10 s apart; otherwise "unknown").

### 07: noisy neighbors

Victims are Guaranteed (1 CPU, requests = limits); hogs ask for 100m and may use 2 CPUs. Under contention the kernel shares CPU time by the requests, which is what the CPU numbers show; nothing shares disk bandwidth that way, which is what the disk numbers show. The summary counts only the victims that shared a node with at least one hog; the results say where each one ran. The hogs are checked before and after the victims measure, from inside each hog's sandbox (`loadgen/hog_probe.py`): its `hog.py` processes in `/proc`; for a CPU hog, the CPU they used over 2 s as the sandbox's own kernel counts it (`utime + stime` in `/proc/<pid>/stat`); for a disk hog, its latest write. A scenario with a hog that was not running is invalid, reported with the reason, and left out. The kubelet's number can't do this job under Kata: it reports 0 CPU for a Kata pod (as it reports 0 MiB in 02), so a VM's CPU has to be read inside the guest. It is still recorded beside each check (`kubelet_cpu_m`), and decides nothing. The hogs run as execd background commands. execd applies a command's timeout to a background command too, and kills its process group when the timeout runs out, so a hog's timeout is longer than its own `--seconds`. `results/noisy.json` and `results/noisy.csv` are written from scratch, so the script refuses a `--runtimes` that would drop a runtime already in them, unless you pass `--replace`.

### Not tested

Kata here is `kata-qemu`, the runtime part 3 measured. Kata with Firecracker is not tested: part 2 installed the QEMU and Cloud Hypervisor runtime classes only.

## Probes

Four smaller scripts in `probes/` answer the questions the measurements raised. Each runs from this directory on a quiet cluster (no sandboxes, server on the baseline), checks the same preconditions, prints its plan, and does nothing more with `--dry-run`. Their output is masked like everything else. They write nothing to `results/`; three of them keep a log in `logs/probes/`.

| Command | What it answers | Server | Time |
|---|---|---|---|
| `uv run python probes/kata_probe.py` | What one Kata sandbox of `02`'s shape asks the scheduler for: its RuntimeClass, overhead, and every container's and init container's requests, plus both nodes' Allocated resources before and after. It prints the arithmetic for the density ceiling. Terminal only. | `--runtime kata-qemu`, back to the baseline in a `finally` | about 2 min |
| `uv run python probes/nft_probe.py [--n 30]` | What the ~60 ms of a `dns+nft` lookup is made of. In one sandbox's egress sidecar it times `nft` runs that commit more and more: list, an empty batch, an empty commit, and the add/delete/add renewal the sidecar does per answer. It traces five renewals with strace, and times lookups of an allowed and a denied name. Every write goes to a throwaway table `inet osb_probe`. An exact allowlist of command forms guards the scripts sent to `nft`, and the sidecar's own ruleset must be unchanged at the end. A short-lived debug pod in `default` reads the node's kernel settings. | not changed | about 3 min |
| `uv run python probes/kata_ceiling.py` | Why Kata density stops at about 12 sandboxes per node with "Insufficient cpu". It fills Kata sandboxes two at a time until one stays unscheduled. Then it dumps the pending pod's resources, its scheduling events, every pod bound to each node with its effective request (under four ways of counting), and `kubectl describe node`, and says whether the numbers add up. | `--runtime kata-qemu`, back to the baseline in a `finally` | about 4 min |
| `uv run python probes/kata_plain.py [--cap 30]` | Whether that early refusal belongs to OpenSandbox or to Kubernetes. It runs the same fill with bare pods and no OpenSandbox: one arm with `kata-qemu`, one with a temporary RuntimeClass `osb-runc-overhead` that adds the same 250m / 160Mi overhead to plain runc. It reads the per-pod CPU the scheduler must be counting from where each arm stops. | not changed (it stays on runc) | about 6 min |

`kata_plain.py` creates the namespace `osb-kata-plain` and the RuntimeClass `osb-runc-overhead`, and its `finally` deletes both. If a run is interrupted before that, delete them by hand:

```
kubectl --context osb-eks delete namespace osb-kata-plain --ignore-not-found
kubectl --context osb-eks delete runtimeclass osb-runc-overhead --ignore-not-found
```

The other scripts' preconditions don't look in `osb-kata-plain`, so check that `kubectl --context osb-eks get namespace osb-kata-plain` finds nothing before the next run. If `nft_probe.py` is interrupted while its debug pod is up, the pod stays in `default`. The script prints the command that deletes it, and the same command is in its docstring.

## Results and charts

The CSVs are large: a full run writes about 20 MB, most of it the per-container samples (`density-containers.csv`, `ladder-containers.csv`, `control_plane-containers.csv`) and `latency.csv`. They are committed as written, so every chart can be redrawn and checked; downsample them before committing if the repository size matters to you.

`results/` and `charts/` are committed. They are written anonymized (nodes as `node-a` and `node-b`, the registry as `<registry>`); `measure.save()` refuses to write a result that holds an account ID, an ARN with one, an IP address, a node name with an IP or a home directory path, and puts it in `logs/` instead. The same scan runs over both folders in the tests (`tests/test_published.py`) and at the end of `99_cleanup.py`. `09_charts.py` draws each chart twice, `charts/<name>-light.png` and `-dark.png`, 1600 x 900 px. Full command output (Terraform, Helm, the load generators) goes to `logs/`, which is gitignored.

## Cleanup

```bash
uv run python 99_cleanup.py                  # also turns Container Insights off
uv run python 99_cleanup.py --keep-metrics   # leaves it on
```

It runs every step whatever the others did (the server's settings first, with no port-forward needed; Container Insights off always attempted) and exits 1 if any failed. It deletes, all scoped to this directory: the sandboxes with `example=opensandbox-stress`; the SigV4 rung's broker-made sandboxes (`script=stress-05_egress_ladder`); the BatchSandboxes `03` made by hand; the Pool `osb-stress-pool`; `06`'s Job and ConfigMap; the latency client pod and its ConfigMap; the echo server `echo-stress` and the VM sampler pods (each by its labels); the snapshot images of this directory's sandboxes (recorded in `results/created-sandboxes.txt`), once the sandbox is gone; and the Container Insights log group `/aws/containerinsights/osb-eks/performance` (`--keep-log-group` keeps it; the metrics stay in CloudWatch). Then it scans `results/` and `charts/`. It keeps part 4's echo server, part 5's broker and images, and part 3's snapshot repository, Secret and controller settings. `../opensandbox-eks/99_teardown.sh` removes everything at the end of the series.

## Tests

```bash
uv run pytest
```

The tests need no cluster: the statistics, the Sampler against a recorded `stats/summary`, the CSV writer, the VM sampler's log parser, the plan filter of `01_metrics.sh`, the preconditions, refusal logic and delivery size, the manifests (rendered and parsed; the VM sampler's script also runs in busybox when Docker and the image are here), the load generators against local stand-ins, the charts from made-up results, the scan of `results/` and `charts/`, every script's `--dry-run` with `kubectl`, `helm`, `terraform` and `aws` replaced by stand-ins that would record a call, and every probe's `--dry-run` under an audit hook that fails on any subprocess, exec or socket call.
